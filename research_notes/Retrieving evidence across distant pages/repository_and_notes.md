# Repository context and contextual notes

## What does this repository actually implement and measure?

### Takeaway

The current architecture already has the right storage boundaries for a small entity or standalone-fact side index. Its principal missing capability for the stated example is an evidence-backed identity link; a generic summary is not that link. Documentation includes historical configurations and some unverified performance claims, so source and versioned evaluation artifacts take precedence.

### Cited Findings

- Main ingestion persists the original parent/child chunks and tree nodes first, then generates child summaries and embeds `summary_text + "\n\n" + content`; `title` is passed into the embedding client. Raw source content and summary are separate database fields. This is a reversible augmentation boundary suitable for adding another retrieval view without replacing source text. [Main ingestion](/Users/proximus/Documents/antigravity/RAG/src/deep_context/ingestion/summary_pipeline.py:62), [embedding payload](/Users/proximus/Documents/antigravity/RAG/src/deep_context/ingestion/summary_pipeline.py:142).
- The stock contextualizer sees the document title, section path, the **first 800 characters of the parent**, and at most 2,500 characters of the target chunk. It does not read the entire book or perform a document-level mention-linking pass. It forces an `In {title} ({section}), ...` opening. Its batched tokenizer truncates inputs at 2,048 tokens. [Prompt builder](/Users/proximus/Documents/antigravity/RAG/src/deep_context/ingestion/summarizer.py:155), [generation](/Users/proximus/Documents/antigravity/RAG/src/deep_context/ingestion/summarizer.py:265). The more elaborate evaluated Variant B is separate and should be described from the other researcher's notes.
- Current code defaults: 150–300-token children, 1,000–2,500-token parents, 15% overlap, summary generation disabled by default, stock summary model Qwen3-0.6B, max 180 generated tokens. These are defaults, not proof of the environment used in the reported experiments. [Settings](/Users/proximus/Documents/antigravity/RAG/src/deep_context/core/config.py:190).
- Main hybrid search retrieves lexical and dense lists for each subquery, uses weighted RRF, deduplicates by chunk ID and identical first 120 content characters, and caps fused candidates. This prefix deduplication is another possible loss point when different pages share boilerplate; it is not a demonstrated cause of the far-page failures. [Hybrid retriever](/Users/proximus/Documents/antigravity/RAG/src/deep_context/retrieval/hybrid.py:37).
- `RetrievalEngine` sends the candidate list into the reranker with a requested output count capped at 24; it does **not** pre-cut the input candidate list to 24 at that point. Parents are resolved and deduplicated afterward, then truncated to requested top-k. The README's diagram of a pre-rerank 24-candidate cutoff does not exactly describe this code. [Engine](/Users/proximus/Documents/antigravity/RAG/src/deep_context/retrieval/engine.py:105), [parent resolution](/Users/proximus/Documents/antigravity/RAG/src/deep_context/retrieval/engine.py:216).
- **Potentially important for the notes result:** the hosted neural reranker receives `candidate.content[:1000]` without `summary_text`, both in the stock integration and the strict evaluation patch. Thus a name introduced only by an annotation can help the first-stage vector/lexical search while remaining invisible to the neural scorer. The 1,000-character limit is another distinct source-visibility boundary. This is an observed code property, not proof that it caused the user's null result. [Hosted scorer](/Users/proximus/Documents/antigravity/RAG/src/deep_context/retrieval/ecohash_reranker.py:45), [strict eval scorer](/Users/proximus/Documents/antigravity/RAG/eval/strict_clients.py:685).
- The scored content is the **raw child chunk**, not the hydrated page/parent. PostgreSQL lexical/vector queries restrict `c.level = 'child'` and return `c.content`; production and strict evaluation rerank before parent expansion. Therefore a target span past character 1,000 of a longer child can be omitted from scorer input, but full-page clipping is not the precise description. [Vector SQL](/Users/proximus/Documents/antigravity/RAG/src/deep_context/storage/postgres_store.py:1204), [lexical SQL](/Users/proximus/Documents/antigravity/RAG/src/deep_context/storage/postgres_store.py:1092), [evaluation ordering](/Users/proximus/Documents/antigravity/RAG/eval/adapter.py:403).
- **Already tested, not an untried fix:** `eval/variant_b/rerank_context.py` adds the generated generic context line before the first 1,000 characters of child text at scorer time. The findings report +0.006 and −0.003 nDCG@10 for the corresponding development comparisons, with no established gain. Do not imply that generic annotation visibility alone will fix the problem. A verified mention-to-entity identity annotation is a different, still-unvalidated intervention. [Existing study](/Users/proximus/Documents/antigravity/RAG/eval/variant_b/rerank_context.py:1), [reported result](/Users/proximus/Documents/antigravity/RAG/eval/variant_b/FINDINGS_WHY_LOWER.md:280).
- The stock resolver returns parent sections, which can cover several pages; it uses parent page metadata before child page metadata. The evaluation's page documents may deliberately differ. Preserve exact evidence-span/page provenance in any new derived view rather than assuming every returned parent is exactly one source page. [Parent resolver](/Users/proximus/Documents/antigravity/RAG/src/deep_context/retrieval/engine.py:242).
- Current PostgreSQL initialization weights raw text B and summaries C in `search_tsv`. `docs/INDEXING.md` instead shows summaries A. The old handoff describes NVIDIA 1,024-dimensional embeddings while current settings use Gemini at 768 dimensions. These are configuration/documentation drift, not a reason to discard all repository documents. ### Inferences

- The stock notes cannot recover an antecedent located only hundreds of pages away because their actual input contains no such evidence. The evaluated glossary adds possible aliases, but a glossary is not proof that **this occurrence** of “he” refers to a particular entity.
- Inspect candidate all-page recall before fusion, after fusion, after reranking, and after page/parent deduplication. A null final result can conceal a gain in discovery that is later dropped; a reranker also cannot retrieve a page that never entered its candidate set.
- Test the reranker using original source plus **verified identity annotation**, with labels separating annotation from source, as a separate ablation beyond the generic context-line experiment already performed. Otherwise the scorer may undo the improvement sought from identity resolution. Hold the scorer token budget fixed and retain the target event span; keep raw-only scoring as a control because false identity annotations can bias the reranker. Report all-evidence candidate recall separately from all-evidence final-page recall to determine where evidence disappears.
- An identity/mention table plus separately embedded, source-backed statements fits these storage boundaries without replacing Google embeddings or introducing a graph database. Suggested fields: document/version ID, entity ID, mention text, source page, offsets/node/chunk ID, antecedent evidence offsets, and a decision/confidence/abstention field. This is an implementation recommendation, not an existing repository table or validated result.

## Why do generated notes help some retrieval tasks and fail this one?

### Takeaway

Useful context supplies **missing discrimination**—entity, company, period, defined term or parent concept. Restating facts already represented by a strong embedder adds little; copying a shared global summary can make pages harder to distinguish. These explanations are compatible with the observed result, but no paper establishes a general theorem that strong embeddings make all contextual notes useless.

### Cited Findings

- **Anthropic Contextual Retrieval, 2024 (author/company experiment):** Claude 3 Haiku was given the whole document and target chunk; usually 50–100 context tokens were prepended for embedding and BM25. Across code, fiction and scientific domains, reported top-20 retrieval failure fell from 5.7% to 3.7% with contextual embeddings, to 2.9% with contextual BM25, and to 1.9% after reranking. The reranked setting retrieves 150 candidates and returns 20. These are different conditions from Gemini Embedding 2, Qwen 2B/9B, and joint recall of two pages ≥100 pages apart; 67% is a **relative failure-rate reduction**, not a 67-point accuracy gain or a small-model reproduction. [Original report](https://www.anthropic.com/research/contextual-retrieval).
- **Reuter et al., NLLP 2025, Towards Reliable Retrieval in RAG Systems for Large Legal Datasets (independent of Anthropic; authors evaluate their own SAC):** On LegalBench-RAG's contracts, NDAs, M&A and privacy policies, a roughly 150-character whole-document fingerprint prepended to 500-character chunks reduced wrong-document retrieval, described as approximately halving mismatch across settings. Generic summaries beat expert-guided summaries. Setup uses GPT-4o-mini, gte-large and FAISS; no reranker/end-to-end QA evaluation. This supports summaries when identifying the correct document among boilerplate near-duplicates; it does not test far-page identity inside one book, small open-model notes or Gemini 2. One summary call per document is inexpensive if the document fits the model context. [Paper](https://aclanthology.org/2025.nllp-1.3/), [full method and limitations](https://aclanthology.org/2025.nllp-1.3.pdf).
- **Zhou et al., February 2026, Beyond Chunk-Then-Embed (independent reproduction; preprint):** Evaluates segmentation and contextualized/late chunking on GutenQA in-document book retrieval and six BEIR in-corpus datasets with four embedding models. Late/contextualized chunking helped many BEIR conditions but hurt GutenQA across tested configurations. Mean relative GutenQA losses by model were −53.17% Nomic, −29.82% Jina-v3, −5.16% Jina-v2, −3.83% E5-large. Authors hypothesize shared document context reduces within-document discrimination. **This is late chunking, not generated-prefix ablation, and these small/open encoders are not Gemini Embedding 2.** It supports caution about context indiscriminately diffusing into every page. [Paper](https://arxiv.org/html/2602.16974v1).
- **Chitale et al., EMNLP 2025 (independent empirical work):** Finds diminishing gains from LLM augmentation with scale; compact retrievers with stronger retrieval pretraining benefit less, and 7B/8B augmentation can rival 70B in its setup. Crucial scope: these are synthetic query–document **training pairs** for compact retrievers, not index-time notes on a fixed Gemini embedding model. Use only as indirect support for diminishing returns, not direct validation of the user's method. [Paper](https://aclanthology.org/2025.emnlp-main.888/), [full scope](https://aclanthology.org/2025.emnlp-main.888.pdf).
- **Chen et al., Dense X Retrieval, EMNLP 2024 (method authors):** Defines self-contained atomic propositions, resolving names/references within facts, and reports better retrieval/downstream QA than passage/sentence units on five open-domain QA tasks with four retrievers over Wikipedia. This is stronger support for **separately searchable fact units** than for generic chunk summaries. However, it is not a long-book identity benchmark, and the 2026 independent comparison above finds proposition segmentation often worse than simple structure-based methods for in-corpus retrieval. Treat selective proposition views as an ablation, not a replacement default. [Dense X](https://aclanthology.org/2024.emnlp-main.845/), [method text](https://arxiv.org/html/2312.06648), [independent comparison](https://arxiv.org/html/2602.16974v1).

### Inferences

1. **Redundancy:** a restatement `f(chunk)` adds no new source evidence. It may change vector geometry usefully, but a strong model may already match the original wording well. Evaluate incremental identity-specific benefit rather than length or fluency of the note.
2. **Identity remains missing:** a name list is a menu of candidate entities. Without an antecedent link, inserting one name is a guess. More fluent summaries can make that guess harder to notice.
3. **Context contamination:** a name or number true on a nearby page can make a chunk match the wrong question. Quote support anywhere in the document is insufficient; the **binding between target mention and entity** needs evidence. Audit that edge separately from “the string exists.”
4. **Shared-document signal can be wasted:** when search is already scoped to one document, title and global synopsis cannot distinguish its pages. A summary helpful for choosing one contract among many can be unhelpful for choosing page 400 instead of page 20 of the same contract.
5. **Competing meanings in one vector:** adding broad summaries mixes target event and background themes into one fixed-size vector. This is a plausible explanation for lower discrimination, not a measured property of the user's specific Gemini vectors.
6. **Pipeline effects:** strong reranking can normalize tiny first-stage ranking differences, or discard annotation-only identity gains because the scorer sees raw pronouns. Candidate-all-evidence recall, then final-all-evidence recall, separates those cases.

### Gaps

- No independent source located that reproduces a few-dollar, single-24GB-GPU Qwen 2B/9B + Gemini Embedding 2 prefix pipeline on ≥100-page-separated identity-dependent evidence.
- Five questions per document are not enough to infer that two variants are equivalent or establish that the better embedder caused the observed lack of gain. The evaluation notes address uncertainty/power.
- No universal architecture is proven equally effective for novels, finance, medicine, legal and policy text. Defined terms/cross-references and clinical abbreviations need different linkage rules and validation from literary pronouns.

## What is compatible with the embedding and cost constraints?

### Takeaway

Keep original vectors and add **small, separately searchable, source-backed identity/fact views** only where necessary. This isolates annotation mistakes and makes a clean experiment cheap. Genuine late chunking is unavailable through this fixed single-vector API.

### Cited Findings

- Google currently documents Gemini Embedding 2 with an 8,192-token input limit, recommended 768/1,536/3,072 output dimensions, text retrieval prefixes, and ordinary vector outputs. Separate `Content` objects give separate embeddings; multiple parts can be aggregated. Gemini Embedding 2 does not accept the old `task_type` field; retrieval formatting is textual. Standard Gemini API text input price is **$0.20 per million tokens**; Batch is 50% of standard. These are API list prices as checked 1 November 2026; Vertex/account billing may differ. [Model](https://ai.google.dev/gemini-api/docs/models/gemini-embedding-2), [format and aggregation](https://ai.google.dev/gemini-api/docs/embeddings), [pricing](https://ai.google.dev/gemini-api/docs/pricing).
- Genuine late chunking encodes long context into **token-level hidden states**, then pools chosen token spans into chunk vectors. The Berlin/“its” example illustrates exactly the local identity loss relevant here, but token access and sufficiently long encoder windows are required. There is no such token-state interface in the stated Google one-vector constraint, and an 8K window cannot directly contain hundreds of pages. “Embed whole book then slice the vector” cannot reproduce it. [Late Chunking](https://arxiv.org/html/2409.04701v3).

### Inferences and concrete proposed budget

- Retain raw chunk vectors. For an accepted identity link, add one short statement such as `entity E17 [canonical name] performs [source event]`, carrying the original chunk/page/offsets **and the antecedent-link provenance**. It can be stored in another Postgres table with its own pgvector index; one vector per statement is compatible with Google. Source quotations remain untouched and final answers cite the underlying page(s), not generated text as evidence.
- Prefer minimal contextual annotations (identity, period, definition/section), not a second paragraph repeating the original. Test separate views against concatenation. With separate views, cap/fuse votes at the source page so five facts on one page do not receive five independent RRF votes or consume five result slots.
- API embedding cost is `0.20 × newly embedded token count / 1,000,000` at the cited standard Gemini API rate. **Calculated example:** one million original/payload tokens plus 100,000 annotation tokens costs $0.22 for that single concatenated index; adding only a separate 100,000-token annotation index to an already built baseline adds $0.02. This excludes retries, overlap, title repetition, repeated variants, GPU rental and generation/evaluation calls. Record actual formatted token volume rather than estimate by page count.
- Small-model annotations are locally billed compute, not free work. Measure model prefill/decode tokens and elapsed GPU hours. Avoid reading the entire 750-page book once for every chunk; process chapters/windows and carry source-backed entity state. At 9B, FP16 weights alone are approximately 18 GB (9 billion × two bytes, calculated), leaving limited 24GB headroom for KV cache/batching; quantization and short contexts may be needed. This is capacity arithmetic, not a promised throughput benchmark.
- A few dollars can readily cover embedding a short side index; graph extraction and large evaluation judges can dominate total cost. Use the existing baseline embedding/reranking caches with versioned payload keys and evaluate retrieval-only changes first. Do not equate caching an earlier result with an independent fresh run.

### Gaps

- No measured token throughput, wattage, GPU rental price, exact corpus token count or cloud bill was observed. Do not promise a fixed runtime or all-inclusive dollar amount.
- The published positive contextualization and proposition results use different generators/encoders and corpora. Small models within the user's limits must earn acceptance on identity-link precision and all-required-page retrieval, not inherit a paper's headline percentage.
